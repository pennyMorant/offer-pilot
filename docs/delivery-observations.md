# 配送完成与耗时汇总

## 关联与口径

自动接单动作发出前，在内存保存一个候选关联：不透明报价指纹、平台、开始时的地区小时分组、单调时钟起点，以及明确的报价总耗时。不会保存报价文字、地址、金额、截图或轨迹。

随后 120 秒内，只有相同恢复槽位指纹和平台的明确接单/配送界面，才能把候选关联提升为当前观测。点击返回已发送不等于配送成功。动作明确未发送或执行异常时清除候选，不生成已完成样本。

明确配送完成后，依照现有“进行中→连续完成界面”的确认逻辑，更新汇总。单次耗时由自动接单动作开始到确认送达界面的单调时钟差得到，包含动作处理和完成页面识别的延迟，不是平台官方配送时长或结算记录。采用本地指纹与当前配送状态关联，尚不能通过平台订单 ID 验证身份；因此存在平台换单但界面无法区分的限制。

手动配送、重启后恢复、候选超时或关联丢失的情况下，仍可记录明确完成的观测，但起点保留未知，不把首次看到进行中页面的时间当作完整配送起点。只有完整计时且报价总耗时可信的样本，才进入配对比较；追加单不使用整单总耗时配对。整组配送仍按一个配送观测处理。

连续 30 秒没有相同配送的明确接单/进行中证据，或停止工作、桥接丢失、采集错误、人工确认无配送，均中断当前观测。中断后再看到进行中状态，可建立起点未知的新观测。故中断次数描述观测区间，不是取消订单数；同一配送可能经历多个中断。新观测不继承旧的完整计时。

进程退出时内存关联丢弃，不建立逐单恢复日志。未获得可靠起点或耗时超出 12 小时范围的完成观测，不计入耗时均值。正常切换页面若超过状态证据窗口，也会损失完整计时样本，这是当前保守关联的限制。

## 持久化

Room 版本 4 新增 delivery_aggregate，粒度为平台、观测起点网格、当地小时起点、时区和测量版本。自动接单候选使用动作开始时分组；起点未知的手动/恢复观测使用首次明确看到配送时的分组，不能将后一种地区称为接单地区。

保存累计字段：

- 确认完成次数、中断观测次数。
- 有完整计时的完成样本数、观测耗时累计。
- 配对样本数、配对观测耗时累计、配对报价耗时累计、观测耗时超过报价的次数。

每个均值仅使用自己的有效样本数。没有原始报价、逐单配送、收入或结算明细。记录默认保留 90 天，沿用按日清理。开发阶段 schema 不兼容时数据库直接重建，不补造历史结果。

## 展示与后续

区域分析页在区域机会和时段趋势中共享平台、地区、星期和时段筛选，报价质量与配送观测分开展示；时区和测量版本保持隔离。耗时比较使用同一批配对样本，不能拿全部报价的平均 ETA 与已接配送的平均耗时直接相减。

这些数据目前不自动修正报价质量标准、预计送达时间或自动接单门槛。没有提取最终收入、小费、车辆实际里程和空驶，不能据此计算实际时薪或净利润。

本阶段仅做源代码、事件连接、字段、均值分母、行数和差异的静态审核；未运行编译、测试或模拟器。
